## 第二轮复评的重点发现

### 桌面入口还没有用上显式任务验收的完整能力

优先级 P1，属于本地开发版的产品接入缺口。

`TaskAcceptance` 能冻结规则、核验产物、执行修改前后反例，并阻止不合格交付；这些路径的回归测试已经通过。但普通桌面对话通过 `agent.loadConfig(projectRoot)` 加载配置，当前未提供显式验收契约的桌面配置入口。已有入口是 CLI 的 `--acceptance-file` 和可信嵌入调用方的 `cfg.acceptance`，相关文档也明确记录“未新增桌面契约编辑器”。

本轮直接使用当前项目配置创建验收器，得到 `acceptance=null`、`status=unconfigured`、`blocked()=false`。因此，普通对话不能仅因这套验收器存在，就被描述为默认受到需求验收保护。现有局部代码校验和 Goal 验收仍有各自作用，不应混为同一种保障。

界面会显示“未配置任务验收 · 需求尚未验收”，这一点是诚实的。问题在于它告知用户缺少什么，却尚未提供桌面内补齐它的路径。

**锐评：验收引擎已经装好，普通用户还缺少接上它的入口。**

建议先支持用户选取测试命令、必需产物和作用范围，经确认后冻结为本轮规则。不要把自然语言直接变成未经确认的可执行检查。验收标准是：不离开桌面即可配置规则、看到修改前后证据，并明确区分未配置、未通过与已通过。

依据：[CLI 契约入口](../../bin/codenode-agent.cjs)、[桌面对话入口](../../electron/ipc/agent.cjs)、[任务验收实现](../../electron/taskAcceptance.cjs)、[现有配置范围说明](../terminal-and-acceptance.zh-CN.md)。

### 后端验证记录没有进入声明的打包范围

优先级 P2，属于本地开发版的打包缺陷；影响验证状态展示，不代表后端本身无法运行。

`electron/backends/diagnostics.cjs` 从相对路径 `../../docs/validation/backend-live-2026-10-18.json` 读取真实任务验证记录，找不到文件便返回 `null`。但 `package.json` 的 Electron 打包文件清单包含 `dist`、`electron`、`config` 等目录，没有包含这份 `docs/validation` 记录。

本轮在临时目录按声明的发行目录结构加载原诊断模块：没有记录文件时，`validationEvidence('hermes', '0.18.2', 'darwin')` 返回 `null`；补入同一份记录后，立即返回三项覆盖范围。若同一后端握手成功，记录缺失会使诊断从“真实任务部分验证通过”退为“仅协议验证通过”。

这解释了为什么源码目录内的后端诊断测试可以全绿，却没有覆盖发行目录中的资源缺失。该复现针对目录布局和诊断函数，本轮未生成安装包，不声称已完成安装包实机验证。

**锐评：源码里能查到的证据，打包后就丢了；可靠性不能只在开发目录里成立。**

建议把受版本控制的验证清单放入明确打包的运行时资源目录，或只打包需要的记录文件。不要将某一版本和平台的历史结果扩展成普遍支持承诺。验收标准是：源目录与打包后的应用资源读取同一份限定范围的记录；缺失与版本不匹配也有专项验证。

依据：[后端诊断实现](../../electron/backends/diagnostics.cjs)、[打包清单](../../package.json)、[现有源码目录测试](../../scripts/core/backend-diagnostics-test.cjs)。

### 答案评分缺口在当前本地版本仍未关闭

优先级 P1，属于 GitHub 默认分支和本地开发版共同的评测缺口。

首轮将长文本问题重点关联到 11 月 2 日报告，容易让人以为它只是历史问题。第二轮重新检查当前 `agent-eval-v3`：同一任务仍要求最多模块编号和总行数，而五类断言依旧只检查读取、压缩、比例、上下文和步数。

本轮离线运行该题，结果为 1/1 PASS。其脚本化最终回复只是“已读取 data/large.txt，内容较长，已按摘要进行处理”，并未给出题目要求的统计答案。这个结果可以证明已测压缩流程运转，不能算作统计任务完成。

**锐评：题目问“答案是什么”，绿灯却只代表“处理过材料”。这个口径至今没有对齐。**

建议保留机制测试，并单列结构化答案正确性；覆盖错误频次、缺少并列项、总行数口径和缺失答案。正确性通过后再统计效率，不让步数指标覆盖结果质量。编码评分器已有独立行为验收，应将这种结果导向扩展到仍有盲点的任务。

依据：[当前长文本任务与断言](../../scripts/eval/agent-eval-tasks.cjs)、[编码评分说明](../coding-eval.zh-CN.md)。本轮离线报告目录为 `/tmp/codenode-review-long-context-20261114`，临时报告不作为长期可复现资源承诺。

### 上一轮判断需要怎样收紧

“功能太多”和“文件太长”可以说明维护压力，但不能单独证明用户体验差或架构错误。矢量绘图是否值得保留，需要明确用户场景；画布是否拖慢普通编码任务，需要实际任务对照。它们仍是合理的产品判断，却应排在本轮可直接定位的入口、评分与打包问题之后。

本地新增的独立编码评分器已覆盖 28 个正反例，本轮全部通过；应撤回任何把项目概括为“只有流程测试”的说法。更准确的评价是：**项目已有扎实的结果验证能力，但覆盖和接入不均匀，尚未形成一致的端到端保障。**

## GitHub 最新默认分支的主要问题

### 功能范围超过了清晰的产品主线

远程版本同时承载工程对话、工作流、Goal、多 Agent、多个执行后端、可选检索、Trellis 兼容与矢量绘图。源码中的矢量编辑器还自行处理贝塞尔曲线、锚点、旋转与参考线。每一项都引入独立的状态、交互和回归成本。

对于 README 明确标注的单人维护项目，这种范围值得收缩。尤其是矢量绘图：应先说明它帮助哪类编码任务、节省哪一步操作，再决定投入深度。当前最值得验证的产品主线是“提出任务、修改代码、核对结果、审阅交付、中断续跑”。

锐评：**核心编码体验还需要打磨时，维护一个绘图编辑器，是很昂贵的分心。**

依据：[远程 README](https://github.com/yimi528/CodeNode/blob/dc4f1de1f325ae429697072b2bcbf862f1626879/README.zh-CN.md)、[远程矢量交互实现](https://github.com/yimi528/CodeNode/blob/dc4f1de1f325ae429697072b2bcbf862f1626879/src/vector/Surface.tsx)。功能取舍属于本次评审判断，不代表已有用户研究结论。

### 核心模块承担的协调责任过重

按文件换行数统计，两份源码的规模如下：

| 文件 | GitHub 默认分支 | 本地开发版 |
| --- | ---: | ---: |
| `electron/agent.cjs` | 4591 | 3233 |
| `electron/subagents.cjs` | 2134 | 2134 |
| `electron/ipc/agent.cjs` | 1901 | 1879 |
| `src/styles.css` | 5142 | 2870 |

行数本身不证明缺陷，但 Agent 循环需要同时协调协议、预算、上下文、工具、审批、取消与恢复，修改时的理解成本确实偏高。本地拆分已经降低部分文件规模，应该认可；远程版本尚未包含这些后续提交。

本地的模块边界测试限制文件增长，可以防止债务继续扩大。但行数门禁只是约束手段。真正需要验证的是职责能否独立说明、依赖是否单向、状态是否有唯一来源，以及变更是否能通过局部行为测试验证。

锐评：**模块拆出去之后，如果修一个问题仍要理解整套运行时，复杂度就没有真正降下来。**

依据：[远程 Agent 核心](https://github.com/yimi528/CodeNode/blob/dc4f1de1f325ae429697072b2bcbf862f1626879/electron/agent.cjs)、[本地模块边界测试](../../scripts/core/module-boundaries-test.cjs)。

### 评测中的流程通过仍可能掩盖答案错误

远程 `long-context-compression` 任务要求统计出现最多的模块编号和总行数，但断言检查的是读取成功、发生压缩、压缩比例、上下文长度和步数，未校验统计答案。这个缺口可以直接从远程源码确认，不依赖本地后续报告。

这些断言可以验证压缩机制运行，但不足以证明压缩后仍保留了解题所需信息。应将答案正确性、运行机制与效率分别评分；先明确题目到底验证哪一种能力，再解释总分。

锐评：**要求模型回答问题，评分却只确认它走过流程，绿灯就可能亮错地方。**

依据：[远程评测任务及断言](https://github.com/yimi528/CodeNode/blob/dc4f1de1f325ae429697072b2bcbf862f1626879/scripts/eval/agent-eval-tasks.cjs)。

### 画布的默认地位需要任务收益支撑

远程 `App.tsx` 将画布、文件工作区、目标总览和右侧对话整合进同一个工作台。对复杂依赖与恢复历史，可视化可能很有帮助；对单个 Bug 修复，用户更可能需要源码、差异、测试输出和下一步操作。

应让简单任务直接进入对话和文件审阅，并让执行记录自动生成可视化视图。画布的价值应体现为更快识别依赖、失败与可恢复步骤，而不是要求用户额外维护一份任务图。

此前对“空画布占主要空间”的评价来自本地已有截图，不能用作最新远程版本的实机体验结论。这里保留的是基于源码结构的产品判断，需要通过真实任务操作验证。

依据：[远程工作台结构](https://github.com/yimi528/CodeNode/blob/dc4f1de1f325ae429697072b2bcbf862f1626879/src/App.tsx)。

## 应保留的工程优势

CodeNode 已把取消、检查点、未知副作用、子任务产物核对和验收证据失效纳入运行设计。这些机制关注真实使用中的失败路径，是值得保留的方向。远程 README 与恢复设计已将它们作为核心定位，而本地开发进一步补充了验收与交付展示。

项目的评测记录也保留失败、源码指纹、评分恢复口径与评分器局限。这种记录方式有助于发现真实问题，应继续坚持。下一步要做的是让这些机制带来可测量的交付收益，并把内部复杂度收在用户操作之外。

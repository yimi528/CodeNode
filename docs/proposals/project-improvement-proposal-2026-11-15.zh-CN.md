# CodeNode 产品与工程改进方案 (2026-11-15)

日期：2026-11-15

面向对象：项目维护者与核心贡献者

文档性质：架构重构、功能取舍与工程落地指南


---

## 1. 现状复盘与改进动因

在近期的技术评测与社区对比中，CodeNode 展现出极其鲜明的技术特质：

### 1.1 必须坚守的独特价值（核心基本盘）
1. **可靠的执行状态机（SRE 心智）**：引入基于内容哈希的检查点机制（`runCheckpoint`）、副作用账本（`sideEffects`）、幂等执行与崩溃续跑，解决了传统 Agent 崩溃后上下文丢失或盲目重放造成二次破坏的顽疾。
2. **非伪造的产物验收体系**：`TaskAcceptance` 机制要求修改前测试红灯、修改后测试绿灯（反例校验），并将验收证据强制绑定到源码指纹（SHA-256）与提交环境；一旦代码变更，证据立即失效，从机制上杜绝了模型“谎报测试通过”。
3. **极度克制与透明的运行时**：摆脱了社区常见的重型框架堆砌（不依赖 LangChain、CrewAI、Docker 依赖等），以纯 Node.js 主进程 + React/Zustand/ReactFlow 实现了极速本地启动与极低资源占用。
4. **统一协议与解耦后端**：自研 Agent 与外部执行器（Codex、DeepSeek Harness、Hermes、OpenCode 等）共享 ACP v1 契约，具备作为统一控制平面的潜力。

### 1.2 当前制约发展的四大核心瓶颈
1. **战线过长与“全能神陷阱”（Scope Creep）**：单人维护状态下塞入了矢量贝塞尔绘图、复杂连线画布、Trellis 兼容、多后端协议等，导致外围代码（如矢量编辑器）严重消耗维护精力，稀释了对核心编码循环的投入。
2. **画布仪式感与编码心智的排斥**：编程本质上是流式、文件树与终端驱动的。将任务强制映射为需要手动维护的连线画布，在单点任务和日常 Bug 修复中增加了不必要的认知摩擦。
3. **底层能力与用户桌面入口断层**：底层的 `TaskAcceptance` 引擎功能完备，但普通桌面对话长期缺少显式验收规则的图形化配置入口；桌面界面能诚实提示“未配置任务验收”，却未给用户提供低摩擦的补齐路径。
4. **评测与发行的保真度缺口**：历史评测中断言曾出现“验证了压缩流程，却未校验长文本统计答案对错”的评分盲点；发行资源打包清单遗漏了部分真实后端验证记录，导致“开发目录全绿、打包安装包降级”。

---

## 2. 改进总原则：从“大而全工作台”到“高可靠交付机”

针对上述瓶颈，确立以下三大改进原则：

```
                ┌──────────────────────────────────────────────┐
                │             CodeNode 核心定位转向             │
                │     AI 编码任务的可靠性与可信交付工作台      │
                └──────────────────────┬───────────────────────┘
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
【原则一：果断剥离自嗨】        【原则二：能力无缝下沉】        【原则三：真实闭环保障】
砍掉矢量绘图等外围负担，        打通桌面端验收配置与交互，      修复评分与打包盲点，
画布降级为只读运行态监控。      让反例验证成为默认体验。        确保真实模型交付可靠。
```

1. **做减法（Cut the Fat）**：坚决冻结并隔离与核心研发交付无关的试验性模块，收缩画布的主观交互地位。
2. **补入口（Bridge the Gap）**：将后端沉淀的检查点、反例测试、副作用账本和交付卡片，转化为桌面端开箱即用的轻量控件。
3. **重交付（Focus on Delivery）**：聚焦于“任务怎么立项、如何可信修改、中断如何无损恢复、交付证据如何向负责人交代”，在团队交接与高风险维护场景建立不可替代的壁垒。

## 3. 具体改进路线图 (P0 -> P1 -> P2)

### 3.1 阶段一（P0：闭环打通与外围止血，建议周期：1~2 周）

本阶段目标：以最小代价打通最核心的能力短板，消除评测失真与打包缺陷，停止外围复杂度的继续蔓延。

#### 任务 1.1：桌面端接入极简“任务验收配置”控件
* **现状**：`TaskAcceptance` 仅在 CLI 和配置式注入中生效，桌面端用户只能看到只读的“未配置任务验收”。
* **改进方案**：
  1. 在对话输入框上方或随任务立项时，提供轻量折叠式 **`任务验收选项 (Acceptance Spec)`**。
  2. 支持三种极简配置模式：
     - **一键套用项目默认**：自动探测并读取 `package.json` 中的 `npm test` 或指定测试脚本。
     - **单命令验证**：用户手动指定本次改动的校验命令（如 `npm run test:my-module`）。
     - **必需产物与范围**：声明本次任务必须创建/修改的目标文件路径，禁止越界写文件。
  3. 任务启动（Run）前将此契约冻结至当前 Run 状态中，驱动 `electron/taskAcceptance.cjs` 执行修改前反例校验与修改后回归。
* **验收判据**：普通桌面用户无需离开 GUI 界面，即可在发起对话时指定验收命令并看到“修改前报错 -> 修改后通过”的完整证据链。

#### 任务 1.2：桌面交互以“交付卡片（DeliveryCard）”为核心出口
* **现状**：代码修改后散落在对话气泡中，用户难以快速评估本轮改动的实际影响与回滚风险。
* **改进方案**：
  1. 强化已有的 `DeliveryCard` 与 `TaskAcceptanceCard`，将其置于每轮 Run 结束后的首要视觉焦点。
  2. 交付卡片聚合四项核心事实：
     - **改动文件列表及哈希**（支持点击查看 Diff）。
     - **测试与验证状态**（明确展示是否执行了修改前反例复现）。
     - **外部副作用提示**（若执行了未登记幂等性的外部网络/命令，明确提示）。
     - **一键回滚操作**（调用 `rollbackPlan` 预览并执行冲突安全的回滚）。
* **验收判据**：用户完成一次多文件重构任务后，能在 10 秒内看懂改动范围、测试真实证据以及回滚入口。

#### 任务 1.3：全面冻结并解耦矢量绘图模块（Vector Surface）
* **现状**：`src/vector/Surface.tsx` 及关联逻辑包含数千行复杂的贝塞尔曲线、锚点吸附、画布旋转代码，与代码编写核心脱节。
* **改进方案**：
  1. 将 `src/vector/` 标记为 `@deprecated` 或直接移至可选插件/实验性目录，禁止主线业务继续向其增加逻辑。
  2. 在构建管线与打包清单中进行按需打包或剥离，减少样式表污染与维护负担。
* **验收判据**：核心构建与类型检查不再受到矢量绘图逻辑影响，主应用打包体积明显下降。

#### 任务 1.4：彻底关闭评测套件与打包资源的真实性缺口
* **现状**：部分长文本任务只断言了上下文压缩流程，未断言回答数据正确性；打包清单缺少 `docs/validation` 真实运行记录。
* **改进方案**：
  1. 优化 `scripts/eval/agent-eval-tasks.cjs`：在长文本或统计类题目中，将“机制运转通过（Mechanism Pass）”与“答案正确性（Answer Accuracy）”分列报告，只有两项均通过才亮绿灯。
  2. 调整 `package.json` 的打包文件列表（`files`），将受版本控制的后端验证数据移入标准运行时资源目录（如 `config/validation/` 或 `electron/assets/`），并增加针对安装包环境的资源探针测试。
* **验收判据**：`npm run eval:agent:repeat` 不再放过错误答案；离线打包后的应用在无源码工作区下依然能完整展示后端诊断证据。

### 3.2 阶段二（P1：架构解耦与心智重塑，建议周期：2~4 周）

本阶段目标：理顺开发者日常使用心智，重构主进程核心模块边界，降低代码复杂度和新参与者的认知负荷。

```
【原有心智摩擦】                         【重构后的自然流】
  用户打开项目                             用户打开项目
       │                                        │
       ▼                                        ▼
 面对空白画布，需思考连线 (卡顿)          直接进入工程文件树与对话输入
       │                                        │
  手动拖拽 Task / Stage 节点              提出任务并指定/默认验收规则
       │                                        │
  启动运行，四处查找状态                  Agent 自动流转，后台生成执行图
                                                │
                                          交付卡片一目了然：Diff + 证据 + 回滚
                                          （可选展开只读执行图排查异常）
```

#### 任务 2.1：画布定位重构——从“操作台”退化为“只读执行与恢复视图”
* **现状**：用户进入工作台时，主区域被大面积画布占据，而普通编码任务不需要排布节点。
* **改进方案**：
  1. 默认视图以 **“代码/差异审阅 + 对话流 + 交付卡片”** 为主面板。
  2. 画布（Workflow Canvas）调整为 **只读的执行与恢复监控面板（Execution Graph Inspector）**：
     - 当 Agent 自主分解子任务或调用多工具时，后台自动绘制拓扑图。
     - 用户点击节点，直接聚焦到该步骤的工具输入、输出日志、检查点（Checkpoint）与改动 Diff。
     - 用户无需也不能手动连线，消除“维护节点拓扑”的心智负担。
* **验收判据**：新用户在不需要了解 ReactFlow 节点概念的情况下，即可流畅完成常见代码修改任务。

#### 任务 2.2：主进程核心模块责任收敛与单向依赖治理
* **现状**：`electron/agent.cjs` 承担过多协调逻辑，协议适配、状态流转、检查点落地、上下文压缩交织。
* **改进方案**：
  1. 严格按单一职责拆分 `electron/agent.cjs`：
     - `electron/agent/reactLoop.cjs`：纯净的 ReAct 状态机循环（只管 Step 与状态跃迁）。
     - `electron/agent/contextManager.cjs`：上下文组装、动态预算计算与历史滑动。
     - `electron/agent/toolDispatcher.cjs`：工具路由、沙箱检查、审批挂起与执行。
     - `electron/agent/recoveryLedger.cjs`：幂等检查点记录、副作用落盘与回滚映射。
  2. 制定严格的依赖规则：工具执行层与恢复层不得反向依赖 UI/IPC 表现层，单文件换行数控制在合理范围。
* **验收判据**：新增一个工具或调整一种模型协议，只需修改对应独立文件，无需全量通读整个 `agent.cjs`。

#### 任务 2.3：强化本地终端与 Shell 执行契约
* **现状**：复杂命令（交互式提示、长耗时服务、环境变动）容易挂起或污染后续状态。
* **改进方案**：
  1. 完善终端执行隔离：显式区分纯命令数组执行（`execFile`，无 Shell 转义风险）与复杂管道命令（`shell: true`）。
  2. 增强命令超时守护、主动取消信号（`SIGINT`/`SIGTERM`/`SIGKILL` 级联击杀进程树）及未关闭后台进程自动排查。
  3. 对非幂等命令（如 `rm -rf`、`git push`、远程网络请求）强制进入副作用账本登记，并主动拦截二次重跑。
* **验收判据**：在 Agent 执行 `npm run dev` 等长命令或被强制 Cancel 时，进程树能被 100% 干净杀灭，不遗留孤儿进程。

### 3.3 阶段三（P2：场景穿透与商业落地验证，建议周期：4~8 周）

本阶段目标：放弃与通用 IDE 拼日常代码补全的劣势战场，主打特定高难度、高价值的研发外包与团队交付场景。

#### 任务 3.1：打造特定高壁垒交付场景模板
* **重点切入场景**：
  1. **跨模块/跨仓库依赖升级**（例如：升级核心依赖版本，自动修复破坏性变更，跑通全部既有测试并附带变更指纹）。
  2. **端到端 Bug 修复与反例固化**（用户给出错误日志，系统先编写必定复现失败的单测，再改业务代码跑通单测，完成自闭环）。
  3. **存量项目架构治理与规约对齐**（依据 Trellis 规范或内部规范文档，自动化扫描、整改并生成合规性报告）。
* **实施方式**：提供预设的 Scenario 模板，内置特定任务的验收规则生成器。

#### 任务 3.2：标准化“团队交接包”与可信报告导出
* **改进方案**：
  1. 将 `.cnode` 工程文件能力外化：支持一键导出包含完备检查点、代码差异、验收证据的 **独立 HTML/Markdown 交付报告**。
  2. 报告明确回答技术负责人的三连问：
     - **做了哪些改动？**（精确到行级 Diff 与影响分析）
     - **凭什么相信它是对的？**（修改前后测试日志、产物 SHA-256、执行环境信息）
     - **有哪些地方需要人工介入？**（未覆盖的边缘用例、未决的外部副作用、已知遗留风险）
* **验收判据**：交付团队向外部客户或团队主管提交该报告时，审阅方无需拉取环境即可核查证据有效性，审阅时间缩短 50% 以上。

## 4. 关键模块演进与架构对照

| 维度 | 当前实现 (0.13.0) | 改进后目标 |
| :--- | :--- | :--- |
| **主界面交互** | 画布为主视觉，对话在侧边，操作偏仪式化 | **代码/Diff/对话为主，画布降级为只读执行图监控** |
| **验收规则配置** | 依赖外部 CLI 参数或代码配置，桌面端只读 | **桌面端开箱即用的轻量验收契约面板（支持单命令/产物声明）** |
| **执行中断恢复** | 后端已有完备检查点，但前端呈现不够直观 | **在交付卡片上直接呈现“恢复点”与“文件回滚影响预览”** |
| **外围非核心模块** | 自带贝塞尔曲线矢量绘图（维护负担重） | **彻底隔离/剥离矢量模块，主仓专注于软件工程主航道** |
| **核心代码组织** | `agent.cjs`（3000+ 行）承担多重交织逻辑 | **解耦为循环机、上下文调度、工具执行与账本四项单向服务** |
| **评测可信度** | 离线断言覆盖率高，但存在部分长文本语义盲点 | **严格区分机制通过与答案正确性，建立防穿透评估门禁** |

## 5. 明确不做的事项（Non-Goals）

为保证单人/小团队资源的高度聚焦，明确以下不予推进的方向：

1. **坚决不在工作台里造“Figma”**：不再开发、优化或扩展任何与软件研发流程无直接关系的图形绘制、矢量排版功能。
2. **不尝试重写或替代 VS Code 编辑内核**：放弃开发完备代码编辑器的幻想，不正面与 Monaco/LSP 原生补全拼手速，编辑操作聚焦于 Diff 审查与局部的修正。
3. **不引入庞大的多进程外部运行依赖**：坚持零 Python 胶水层、零容器硬性依赖的本地 Node.js 极简设计，保持双击即启的轻快体验。
4. **不搞空中楼阁式的“无人自主软件公司”多 Agent 聊天**：所有的子 Agent 协作必须建立在“产物文件落盘校验、接口显式 Contract 校验”的基础上，严防无状态的纯文本循环空耗 Token。

## 6. 成功度量指标 (Success Metrics)

| 指标类型 | 具体指标 | 目标值 | 验证方式 |
| :--- | :--- | :--- | :--- |
| **产品可用性** | 桌面端创建任务并配置验收规则耗时 | < 30 秒 | 桌面实机交互操作统计 |
| **恢复可靠性** | 任务强杀/网络断开后一键续跑成功率 | 100%（无重复破坏） | 自动化中断注入与重放测试 |
| **验收真实性** | 评测套件中答案真实正确率与报告一致性 | 100%（杜绝虚假 Pass） | 引入独立 Grader 自动化复核 |
| **工程健康度** | 核心文件行数门禁 | 单文件 ≤ 1500 行 | `npm run test:module-boundaries` |
| **交付可信度** | 交付卡片生成率及证据指纹有效性 | 100% 覆盖非只读 Run | 端到端交付工作流回归测试 |

---

**总结**：CodeNode 拥有全社区极为罕见的工程韧性基底。通过本方案的“**减外围、通入口、强交付**”，项目能够迅速摆脱自嗨与散焦，成为每一位追求确定性交付的专业开发者与研发团队最趁手的“Agent 任务 SRE 护航者”。

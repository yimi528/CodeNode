# CodeNode 会话历史分支与工作区状态改进建议

## 摘要

CodeNode 可以借鉴 Flowing 将会话历史组织为树的思想，但不应只把线性消息列表替换成 `parent_id` 结构。编码 Agent 的会话会产生文件修改、命令执行、测试结果、用户审批和外部系统副作用；如果会话分支与工作区状态没有同步分离，树形历史会呈现出与真实代码不一致的“伪分支”。

建议采用三层架构：

1. **不可变事实日志**：保存原始消息、工具调用、文件变更、测试证据和审批记录。
2. **可分叉的会话视图**：保存分支、当前游标、上下文可见性、摘要和修订关系。
3. **与分支绑定的工作区状态**：每个可执行分支绑定 Git commit、worktree、补丁集或文件系统快照。

这一方案的目标是让用户能够从任意可靠检查点尝试另一种实现，比较多个方案，采用其中一个并保留完整证据，同时避免失败尝试和过期信息持续污染模型上下文。

## 需要解决的问题

### 线性历史容易积累上下文污染

编码会话常按以下方式增长：

```text
需求 → 调研 → 错误尝试 → 修正 → 需求变化 → 再次修正
```

模型在后续回合中仍可能看到已否定的方案、旧文件内容和失效约束。简单截断虽然节省上下文，却会丢失为什么放弃某个方案、哪些命令已执行以及哪些测试曾经失败。

### 会话状态与代码状态可能分离

如果从同一条消息分出方案 A 和方案 B，但两个分支继续操作同一工作目录，那么两个分支看到的会话不同，读写的文件却互相覆盖。此时会话树无法准确回答以下问题：

- 某条结论基于哪个代码版本？
- 某次测试验证的是哪份补丁？
- 切回旧分支时应恢复哪些文件？
- 合并方案时采用的是聊天内容还是实际产物？

### “删除历史”会破坏审计和因果关系

一条看似普通的消息可能关联工具调用、文件修改、用户批准和外部副作用。物理删除或原地改写会导致工具调用与结果失配，也会使事后无法解释代码为何变成当前状态。

## 设计原则

### 事实不可变，视图可调整

原始执行事实采用追加写入，不允许原地覆盖。用户的删除、隐藏、修订和摘要操作只改变会话视图及上下文投影，不销毁原始证据。

### 分支必须同时隔离会话和工作区

创建可执行分支时，同时建立工作区基线。优先使用 Git worktree；不能使用 Git 时，可退化为 copy-on-write overlay、补丁集或内容寻址快照。

### 当前代码和真实验证结果优先于模型陈述

“模型说已完成”不能作为完成证据。分支状态应由文件哈希、Git diff、命令退出码、测试报告或外部系统回读结果确定。

### 上下文裁剪不等于历史删除

模型上下文只需读取当前分支的祖先路径、固定约束和必要证据。旁支、失败尝试和已压缩区段可以不进入上下文，但仍保留在事实日志中供查询和审计。

### 树作为默认结构，DAG 支持结果合并

普通对话节点只有一个父节点，保持树形结构简单可读。只有当多个 Agent 或多个方案共同贡献最终结果时，才创建具有多个父节点的合并检查点。

## 建议架构

```text
不可变事件日志
  消息 · 工具调用 · 文件变更 · 测试 · 审批 · 外部回执
                         │
                         ▼
会话与分支投影
  branch head · active path · revision · hidden · summary · merge
                         │
                         ▼
上下文构建器 ───────────────→ 模型
  当前路径 + 固定约束 + 当前仓库事实 + 按需证据
                         │
                         ▼
工作区管理器
  commit · worktree · overlay · patch · artifact · validation
```

事实日志是唯一证据源；会话树、分支列表、时间线和 UI 均为可重建投影。工作区管理器负责保证会话节点引用的代码状态仍然存在且可验证。

## 核心数据模型

### 历史节点

```ts
type HistoryNode = {
  id: string
  parentIds: string[]
  kind:
    | "user_message"
    | "assistant_message"
    | "tool_call"
    | "tool_result"
    | "checkpoint"
    | "summary"
    | "revision"
    | "merge"
  contentRef: string
  branchId: string
  workspaceRef?: string
  effectRefs: string[]
  evidenceRefs: string[]
  agentId?: string
  modelId?: string
  createdAt: string
  contextVisibility: "normal" | "pinned" | "hidden" | "summary_only"
}
```

`parentIds` 在普通节点中只有一个元素；合并检查点可以包含多个父节点。大段工具输出、媒体和补丁应存入内容寻址对象仓库，节点只保存引用。

### 会话分支

```ts
type ConversationBranch = {
  id: string
  name: string
  headNodeId: string
  baseNodeId: string
  workspaceRef: string
  status: "active" | "paused" | "accepted" | "rejected" | "stale" | "archived"
  createdFromBranchId?: string
  createdAt: string
}
```

### 工作区快照

```ts
type WorkspaceSnapshot = {
  id: string
  repositoryId: string
  baseCommit?: string
  headCommit?: string
  worktreePath?: string
  patchRef?: string
  treeHash: string
  dirty: boolean
  validationRefs: string[]
  createdAt: string
}
```

工作区引用必须能够检测漂移。当实际文件状态与 `treeHash` 不一致时，分支应进入 `stale` 或 `dirty` 状态，禁止静默恢复为“可验证”。

## 关键行为设计

### 创建分支

用户在一个可靠节点上选择“从这里尝试另一种方案”时：

1. 验证节点关联的工作区快照仍可恢复。
2. 建立新 branch，并把 `baseNodeId` 指向该节点。
3. 创建独立 Git worktree 或文件系统 overlay。
4. 在新分支写入 checkpoint，记录需求、基线 commit、未完成事项和允许的写入范围。
5. 从该 checkpoint 开始构建模型上下文，而不是复制完整会话文本。

如果无法恢复对应代码状态，应允许创建“只读推理分支”，但不得允许它直接修改当前工作区。

### 切换分支

切换操作必须同时改变：

- 活跃会话 head；
- 当前工作区或 worktree；
- 工具执行目录；
- 上下文构建路径；
- 终端和测试结果的归属分支。

切换前应检查当前分支是否存在未保存修改，并提供提交、保存为补丁、继续保留或取消切换的明确选择。

### 修剪与修订

建议将 Flowing 风格的操作收敛为以下安全语义：

| 操作 | CodeNode 建议语义 |
| --- | --- |
| Branch | 创建会话分支及隔离工作区 |
| Insert | 仅补充注释、审批、检查点和系统事件 |
| Update | 创建 revision 节点，不覆盖原消息 |
| Remove | 写入 tombstone 或设为 `hidden`，不物理删除 |
| Reparent | 默认禁止，仅限通过一致性校验的管理操作 |
| Compact | 创建带来源范围的 summary 节点，原始节点保留 |

工具调用节点与工具结果节点必须保持配对。隐藏其中一方时，上下文投影应同时处理整组调用，避免向模型发送不完整协议记录。

### 合并方案

合并的对象应是代码、结构化结论和验证证据，而不是两段聊天文本。建议流程：

1. 比较各分支的 Git diff、测试结果、风险和约束满足度。
2. 用户或 Reviewer Agent 选择接收的产物。
3. 在目标工作区执行 Git merge、cherry-pick 或补丁应用。
4. 重新运行验证，不能复用源分支的成功状态冒充目标分支已验证。
5. 创建多父节点的 merge checkpoint，记录采用内容、舍弃内容、冲突处理和新验证结果。
6. 后续上下文从 merge checkpoint 继续，而不是加载所有父分支全文。

## 上下文构建策略

每次模型调用建议按以下优先级组装上下文：

1. 当前目标、用户明确约束和安全边界。
2. 当前分支最近的可靠 checkpoint。
3. checkpoint 到当前 head 的活跃路径。
4. 当前仓库状态、相关文件和最新测试事实。
5. 被引用的旁支结论或证据。
6. 工具定义和本轮所需能力。

默认不加载：

- 未被引用的旁支全文；
- 已否定且已总结的尝试；
- 可由文件或命令重新读取的陈旧输出；
- 与当前任务无关的大段工具日志；
- 已被更新版本取代的模型结论。

摘要节点必须保存 `summaryOf` 范围、生成模型、生成时间和源节点引用。摘要只用于提高读取效率，不能替代测试结果、用户审批或外部回执。

## 用户体验建议

### 时间线保持简单，分支按需展开

默认界面仍显示当前路径，避免把普通用户暴露给复杂图结构。只有发生分叉或用户打开“历史分支”时，才显示树形视图。

### 每个分支展示可比较的工程结果

分支卡片应优先展示：

- 方案名称和目标；
- 相对基线的文件 Diff；
- 测试通过情况；
- 风险和未完成事项；
- Token、时间和工具消耗；
- 当前状态及过期原因；
- “切换”“比较”“采用”“归档”操作。

### 提供明确的安全动作

建议提供以下用户动作：

- 从这里尝试另一种方案；
- 保存当前状态为检查点；
- 仅从模型上下文隐藏；
- 将一段历史压缩为摘要；
- 比较两个分支；
- 采用此分支；
- 放弃但保留证据；
- 基于新代码重新验证。

避免使用含糊的“删除”“恢复”和“合并会话”，因为这些词无法说明是否影响代码、证据或上下文。

## 分阶段实施路线

### 第一阶段：安全的分支基础

- 建立不可变事件日志。
- 为消息增加 `parent_id` 和 `branch_id`。
- 保存 branch head 和 active branch。
- 支持从历史节点创建只读分支。
- 上下文只读取当前祖先路径。
- 支持软隐藏和可追溯摘要。

这一阶段不允许在历史节点之间任意重挂，也不处理多父节点合并。

### 第二阶段：工作区一致性

- 分支绑定 Git commit 和独立 worktree。
- 工具调用强制携带 branch/workspace 身份。
- 记录文件树哈希、补丁和验证结果。
- 检测外部文件修改及陈旧分支。
- 支持分支切换、Diff 比较和分支归档。

### 第三阶段：方案采用和多 Agent 协作

- 支持 Reviewer Agent 独立检查分支产物。
- 支持代码级 cherry-pick、merge 和冲突处理。
- 创建多父节点 merge checkpoint。
- 支持子 Agent 每人占用独立分支或 worktree。
- 把 Agent 结论、代码产物和验证证据分开交付。

### 第四阶段：智能上下文管理

- 根据节点重要度和当前任务选择上下文。
- 自动识别已失效事实并提示重新读取。
- 对大型工具结果按需检索，而不是整段注入。
- 使用真实 Token 用量评估摘要和裁剪效果。
- 支持分支级检索和跨分支证据引用。

## 验收标准

### 正确性

- 从任意 checkpoint 创建分支后，原分支文件不发生变化。
- 切回分支时，会话 head、工作目录和工具执行目录保持一致。
- 工具调用和结果始终配对，崩溃恢复后不存在悬空调用。
- 被隐藏或摘要的历史仍能追溯到原始记录。
- 分支代码漂移能够被检测并明确标记。
- 合并后必须重新验证目标工作区。

### 可用性

- 普通线性会话不增加明显操作负担。
- 用户可在三次操作以内创建、比较并采用一个分支。
- UI 能解释“删除”“隐藏”“归档”和“放弃”的不同影响。
- 用户可以看到某项代码修改来自哪个分支、Agent 和验证结果。

### 性能

- 当前路径上下文构建不需要扫描完整历史。
- 大型工具输出不会在每轮重复加载。
- 创建分支优先使用低成本 worktree 或 copy-on-write 机制。
- 事件日志增长不显著拖慢当前会话读取，可通过索引和快照重建投影。

## 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 分支数量失控 | 默认折叠、自动归档、设置活跃分支上限 |
| worktree 占用空间 | 共享 Git 对象、定期清理已归档工作树、保留补丁和元数据 |
| 摘要遗漏关键约束 | 固定用户约束，摘要保存来源，证据按需回读 |
| 外部命令产生不可逆副作用 | 副作用工具增加审批、幂等键和回执，不承诺随分支回滚 |
| 多 Agent 并发写入冲突 | 每个分支独立工作区，合并前验证写入范围和基线版本 |
| 历史图过于复杂 | 默认展示当前路径，DAG 仅用于合并检查点 |
| 隐私或凭证进入历史 | 凭证走独立注入通道，日志写入前执行脱敏和访问控制 |

## 不建议首期实现的能力

- 任意拖拽消息改变父子关系；
- 物理删除中间消息；
- 自动合并两段自然语言会话；
- 在共享工作目录中并行执行多个可写分支；
- 根据模型自述自动判定任务完成；
- 在没有代码快照的情况下承诺精确回到任意历史节点；
- 默认把整棵树发送给模型。

## 建议结论

树形会话历史值得成为 CodeNode 的基础能力，但产品定义应从“可随意修剪的聊天树”提升为“可验证的编码轨迹”。最小正确闭环不是消息分叉，而是：

```text
可靠检查点
→ 会话与工作区共同分支
→ 独立执行和验证
→ 比较真实产物
→ 采用或放弃
→ 保留完整证据
```

优先完成不可变事实日志、分支与工作区绑定、当前路径上下文构建和软修剪；在这些基础稳定后，再引入多 Agent 合并和自动上下文优化。

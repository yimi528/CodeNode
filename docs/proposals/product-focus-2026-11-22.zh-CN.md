# CodeNode 下一阶段建议：先把一次交付做顺

建议暂停新增功能。下一阶段只回答一个问题：**我已经在用 Codex 或 Claude Code，下次修 bug 时，为什么还愿意先打开 CodeNode？**

我认为最值得验证的理由是省掉收尾时的反复确认。写代码交给开发者熟悉的 Agent。CodeNode 帮开发者看清它改了什么、哪条要求验过了、哪里还要自己拿主意。这个理由能否成立，要看真实使用。现在就投入通用框架或继续扩充自研 Agent，都容易把这个问题推迟。

## 先打磨收工的那一分钟

用一个例子检查现有体验。开发者交代了两件事：“修好导出崩溃；以前保存的工程也要能打开。” Agent 修改了代码，导出测试通过。这时开发者打开本轮结果，应该能直接看到改了哪些文件、导出测试的结果，以及旧工程是否真的打开验证过。如果还没试，写清“旧工程兼容性待验”，就已经帮上忙了。如果有人回滚了改动，还应能看出哪些结果需要重查。

从现有的“本轮交付”和“任务验收”入手。亲自走一遍从派活到决定收工的流程，记下第一次不得不翻聊天、找测试输出或重新输入要求的地方，先修这一处。如果为一次简单修复配置检查所花的时间，比自己打开旧工程还久，就优先简化这一步。[现有交付流程](../task-delivery.zh-CN.md)

## 现有功能怎么取舍

| 建议 | 第一批看什么 | 判断依据 |
| --- | --- | --- |
| 优先打磨 | 打开项目、把任务交给常用 Agent、查看改动和验收结果、继续修改 | 从开始到收工都要用，少找一次就有收益 |
| 按需展开 | 画布编排、多 Agent 分工、高级模型设置 | 一个 bug 可以直接开工；有阶段依赖或明确分工时，再打开对应工具 |
| 暂停投入 | 自研 Agent 的新编码能力、更多后端、把现有代码抽成通用框架 | 先验证已经接入的一个 Agent 能否让人愿意持续使用 CodeNode |
| 合并或删除 | 实际使用中遇到的重复入口、填完后无人使用的字段 | 先移出默认流程；确认现有工程能正常打开、原任务仍能完成，再决定是否删掉实现 |

## 用接下来的三个真实任务做决定

挑一个日常小修、一个带兼容性要求的改动、一个需要隔天接手的任务。开始前写下怎样才算做完。尽量沿用同一个 coding agent，用平时直接使用它的方式作参照。把配置和填表的时间也算进去。每个任务结束后，只记三件事：

- 从 Agent 交活，到我敢确认完成，花了几分钟？
- 哪条要求差点漏验？是谁发现的？
- 下次遇到同类任务，我会主动打开哪个工具？为什么？

三个任务足够暴露最碍事的步骤，样本还小，结论只用于决定下一轮投入。如果兼容性检查或隔天接手反复省了时间，就集中打磨那个场景。若把最碍事的一步修顺后，自己仍习惯直接打开 Codex，而且说不出少了 CodeNode 会多做哪件事，就暂停产品扩张，留下能复用的部分。

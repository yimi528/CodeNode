# CodeNode Agent 效率与任务完成率改进方案

日期：2026-10-30

状态：预算感知压缩、文件读取缓存版本校验、旧工具结果快照、预算主动收尾与无进展观测提示已完成离线实现，任务工作状态、搜索／目录缓存版本边界、恢复会话归档与持久化评测恢复也已完成实现；冻结的原生功能 A/B 已完成，尚未证明整组稳定收益，行为改动保持显式试验。

当前默认策略（2026-10-31）：缓存版本校验等正确性修复保持启用；预算触发压缩、主动收尾、旧正文回收、无进展提示和工作状态这五项会改变求解过程的行为保留独立实验开关，未配置时默认关闭。本批对照未证明整组行为稳定优于基线，不按“已实现”直接推定可以默认推广。显式配置为 true 的项目设置仍可启用对应实验功能。

首项实现范围（2026-10-30）：复用已有压缩流程，在保守预留口径预计剩余不超过 3 轮时评估一次回收。只有预计两轮输入节省能覆盖摘要成本，且余额能承担摘要及后续两轮请求时才尝试；这是首版规划参数，尚未经真实任务校准。摘要失败或未减少输入时保留原历史，每个运行最多一次预算触发尝试。摘要和后续请求共用原 Token／费用账本，规划并不预先锁定后续额度。每轮记录 `request_budget_plan`，回收后记录 `budget_compaction_result` 及重算的输入预留和预计剩余轮数。`agent.compact.budget_aware` 当前默认 false，显式 true 可启用新增触发。本批 A/B 已完成，来源与结果见下方验证结论。

后续补齐（2026-10-30）：已有重复结果引用继续复用；本次增加 `read_file` 缓存命中前的来源版本校验，按原始文件字节 SHA-256 比对，不能仅依赖大小或时间戳。外部修改、删除、路径重新定位或校验不可用时，重新执行原工具并返回当前结果；原有写工具触发的整表失效继续保留。后续已将版本边界扩展到搜索等缓存：使用有界内容指纹，快照不完整时不复用；目录每次刷新。单文件缓存继续使用原始字节 SHA-256。

旧结果快照首版（2026-10-30）：本次运行产生的 `read_file`、`search_files`、`find_files`、`execute_shell` 和 `poll_job` 成功文本结果，超过 8000 字符且位于保护尾部之外时，可将当时模型可见的正文保存到 `.codenode/runs/tool-results/<sha256>.txt`，用路径、来源版本／范围、命令／退出码及首尾片段替换旧正文。复用现有 `read_file` 分页读取历史快照，不重新执行原命令；原始工具记录保持完整。最近完整操作组、失败／部分失败、运行中的任务和取回的快照正文不回收。当前工具面没有 `read_file`、落盘失败、已有文件校验失败、单份超过 2 MiB 或每次运行归档累计超过 16 MiB 时保留原文。`agent.context.archive_results=false` 关闭本功能；快照随运行数据保留，不自动删除。成功结果的来源元数据按内容、调用编号及参数保存为本地日志；新的运行可从恢复消息和匹配日志重建归档依据。没有成功证据的旧版历史仍保留原文，不猜测成功状态；尚未证明真实任务完成率收益。

预算主动收尾首版（2026-10-30）：完成至少一次工具调用后，先执行已有回收流程，再按本轮实际输出档位估算下一请求，并为精简交接输入及最多 2048 输出 Token 规划余量。余额无法同时承担两者时进入 `budget_wrapup` 阶段，最多发送一次不带工具、无重试和无模型切换的请求，只整理待核对事项和下一步建议。事实部分直接来自真实工具记录与现有自动校验报告；不额外执行测试，过期或缺失报告不能当作通过。余额不足、费用预检拒绝、响应异常或格式不合规时退回本地收尾；硬性 Token／费用／重试上限也提供本地交接。交接请求继续使用原预算账本；这是规划余量，不是并发场景下锁定的额外配额，实际请求仍须通过原硬检查。保存可用检查点并以 `LIMIT_REACHED` 终止，保持未完成与可续跑语义。`agent.budget.wrap_up=false` 关闭新增行为。该阶段未新增 UI 运行状态枚举，也未验证真实完成率收益。

无进展观测首版（2026-10-30）：新增可显式开启的 `agent.no_progress.enabled`，`agent.no_progress.rounds` 默认 3（范围 2–20）。连续工具轮次仅出现近期见过的“归一化参数＋原始结果／退出码／错误码＋来源版本”组合时累积计数，达到阈值提示先交代假设依据，再尝试缩小复现、检查调用链或更换验证策略。覆盖同一调用与 A/B 循环；新证据、来源版本变化（包括在两个旧版本之间切换）、用户插话或计划版本更新会重置计数。运行中的后台任务、子代理和交互等待排除在外。命令轮次复用已有有界代码／配置快照，并纳入已观察到的文件路径；快照不完整或不可用时跳过该轮检测。该快照不覆盖所有未知数据文件，严格结果匹配也可能漏掉仅带不同时间戳的相似错误；首版不声称识别全部语义空转。

检测不新增模型调用，也不硬性终止或禁止工具；每运行最多发出两次策略提示，历史中只维护一条提示。`no_progress_observation`／`no_progress_detected` 事件用于观察触发与排除原因。检测状态只在当前运行内保存；开启后的主请求会包含提示，并仍受原预算约束。此为观测和提示版本，真实减少空转的收益与误报率待评测。

剩余工程项（2026-10-30）：`agent.working_state.enabled` 当前默认关闭，显式 true 可开启，在原请求中维护唯一的简短工作状态，包含目标、相关文件、待验证假设、修改、命令检查与下一步。通过 `update_plan` 的可选 `hypothesis` 字段显式记录假设，并标注模型陈述尚未核实；自动状态关联真实调用编号。状态保存到运行文件和对话检查点，恢复的检查仅作为历史，不能自动变为当前版本通过。关闭开关恢复原行为，不增加模型调用。

评测恢复提供原子阶段状态、运行进程锁、解题 Docker 文件系统快照、原代码／任务／测试／镜像指纹和独立评分输出；已有解题尝试不自动重跑。SWE 文件系统任务可仅恢复评分，依赖活进程或额外 verifier 凭据的环境明确拒绝不完整重放。评分依赖网络失败且没有测试执行证据时单列 `startup_failed`，保留原始 reward。真实 Docker smoke 已验证解题后快照恢复、官方 verifier 得分和零额外模型请求。原生 A/B 入口冻结同一份运行时，在相同模型、题目、镜像、预算和首次尝试规则下比较整组功能开关，不据此分离单项贡献。

本批验证结论（2026-10-31）：9 道有效题、两组各一次首次模型尝试，共 18 次。7 个 Node 安装 DNS 失败槽位在确认尚无 Agent 执行／模型日志／用量后，以同一已验证的离线 Node 归档补齐首次求解，原环境失败仍保留。首次评分为基线 4/9、改进 3/9；PyPI 独立评分恢复为 1、压缩器恢复仍为 0，两项均不调用模型，计入评分恢复后为 4/9 对 4/9。两组各一次模型请求超时；预算停止为 3 对 2，成功语义压缩次数均为 0。小样本、已见题、整组开关和基础设施异常限制归因，不能据此宣称各单项无效或费用降低，亦未达到默认推广门槛。

## 1. 背景与证据

检查点边界补齐（2026-10-31）：实际检查点单条消息上限为 6000 字符，工作状态压至 5000 字符内保持 JSON 完整；大段成功结果在截断前保存完整正文，检查点用完整 SHA-256 引用，避免相同前缀不同尾部混淆。恢复时核验原文、来源调用和参数；非零命令退出码不视为成功回收。此修复经过真实检查点往返回归，未混入已经启动的 A/B 冻结版本；实验报告会单独说明来源差异。

## 2. 目标与约束

第一阶段保持同样模型、600000 Token 总上限和现有工具权限，验证减少重复上下文与提前回收是否能改善任务完成率。

目标按以下顺序衡量：

1. 保住已有成功题，避免压缩丢失约束或正确修改。
2. 减少因下一轮预算不足而提前结束的运行。
3. 在同一资源上限下提高独立测试通过率。
4. 降低每个成功任务消耗的累计 Token 和无进展轮数。

所有摘要、重试、验证提示和后续模型请求都计入同一运行预算。缺少供应商 usage 时保留保守结算；已有费用上限、取消和权限约束继续生效。官方隐藏测试与评分反馈不能作为 Agent 解题过程中的提示。

## 3. 优先级与实施顺序

| 优先级 | 工作项 | 主要交付 | 主要验收依据 |
| --- | --- | --- | --- |
| P0 | 预算感知压缩与收尾 | 运行预算预警、回收、重算和受限收尾路径 | 相同预算下减少提前停止，已有成功题不退化 |
| P0 | 重复上下文回收 | 可取回的工具产物、版本化引用、分段输出策略 | 重复正文与每轮输入体积下降，内容保持可取回 |
| P1 | 最小复现与验证闭环 | 假设、修改、针对性测试和结果的简短状态 | 更早出现有效复现和正确修改，真实通过率改善 |
| P1 | 无进展检测 | 进展信号、策略切换与有界循环恢复 | 重复无效操作减少，不误拦正常异步等待 |
| P2 | 持久化评测与恢复 | 幂等任务状态、产物检查点、评分启动失败识别 | 中断不丢结果，恢复不重复付费推理 |

现有实现已经具备压缩、工具缓存、文件与命令输出分页。实施时优先扩展这些组件，避免再建立一套相互竞争的预算或缓存机制。

## 4. P0：预算感知压缩与收尾

### 4.1 触发条件

同时考虑两个维度：

- 当前输入是否接近模型上下文窗口。
- 剩余运行预算是否还能承担后续有效工作、必要的压缩和最终交付。

新增预算触发条件时，可用“预计还能完成的有效轮数”作为规划信号。例如预测剩余预算不足以支持未来 3 轮时评估回收；具体参数通过实验校准，不直接作为固定默认值。

规划估算与硬性预算预留分别记录。第一轮保留现有保守预留算法，先验证内容回收的收益；模型分词器或估算校准作为后续独立实验，避免同时修改计量口径与求解行为。

### 4.2 回收顺序

1. 请求前计算剩余额度、下一轮输入预留及输出额度，记录各部分占用。
2. 优先执行不调用模型的去重与旧结果替换，保留可取回的原始产物。
3. 若仍紧张，且摘要成本可负担、预计节省大于开销，再调用已有语义压缩。
4. 保留任务约束、当前修改、关键错误、测试命令与结果，以及最近完整的工具操作组。
5. 重算预算。能够继续时恢复解题；接近结束时转入验证和交付。
6. 确实无额度时保存检查点，明确记录停止原因与尚未完成事项。

压缩需要提前安排。等剩余预算已经不足以发送旧历史时，摘要请求本身也可能无法发出。

### 4.3 正确性要求

- 压缩费用计入原始运行总额，不能开一个额外预算绕过上限。
- 设置有界恢复次数，首版可只允许一次预算救援，避免压缩循环。
- 压缩失败后有确定的降级或退出路径，不不断重试同一请求。
- `assistant.tool_calls` 与对应的 `tool_call_id` 结果成组保留，不制造孤立工具消息。
- 文件版本、未提交修改、当前假设、失败反例和用户验收条件有明确来源。
- 用户取消立即生效，不能因回收流程重新启动已取消的任务。

首批改动位置：

- [agent.cjs](../../electron/agent.cjs)：把运行预算预警接入现有压缩和请求前流程，增加受限收尾状态。
- [requestBudget.cjs](../../electron/requestBudget.cjs)：提供规划需要的快照和拒绝原因，继续负责最终预留与结算。
- [compaction.cjs](../../electron/compaction.cjs)：复用摘要和完整工具组保留逻辑，增加预算触发来源的观测信息。

## 5. P0：减少重复内容进入后续请求

### 5.1 工具产物与引用

原始文件片段、长命令输出和测试日志保存到运行产物。模型上下文优先保留：

- 路径、版本或内容哈希、读取范围。
- 命令、工作目录、退出码、关键错误及结果摘要。
- 获取更多内容所需的产物引用和分页游标。

较旧的大段正文可以替换为引用；最近编辑所依赖的精确片段与关键失败信息继续保留。引用必须能真正取回内容，不能只有一句“之前读过”。

### 5.2 复用现有分页与缓存

- 搜索先定位，再读取函数、类或报错附近的范围。
- 同一文件相同版本的重复读取，优先提示已有片段；文件变化后立即失效。
- 命令默认返回退出码、错误附近内容与输出摘要，需要时展开完整日志。
- 对重复结果做上下文去重，避免缓存命中了却仍把整段正文反复发送。

缓存键需要考虑文件内容、工作目录以及相关输入版本。写操作和未知副作用命令不能被当作普通只读请求缓存；外部文件变更也不能静默返回过期内容。

主要涉及 [readFileTool.cjs](../../electron/tools/impl/readFileTool.cjs)、[searchFilesTool.cjs](../../electron/tools/impl/searchFilesTool.cjs)、[executeShellTool.cjs](../../electron/tools/impl/executeShellTool.cjs)、[contextBudget.cjs](../../electron/contextBudget.cjs) 与主循环现有去重逻辑。

## 6. P1：最小复现、验证闭环与无进展检测

### 6.1 每个任务保留简短工作状态

工作状态包含目标、相关文件、当前假设、已做修改、最近验证结果与下一步。它是可追溯的任务记忆，不替代原始需求、精确代码和测试证据。

推荐求解顺序为：定位入口 → 构造最小复现或可执行验收点 → 小范围修改 → 运行针对性测试 → 根据具体反例继续修复 → 必要回归。

验证来自项目可见测试、任务说明和 Agent 自行构造的用例。独立 benchmark verifier 继续在解题结束后执行，不能把其隐藏测试或参考补丁反馈给模型。

### 6.2 以实际变化判断进展

跟踪代码差异、错误签名、测试结果和假设变化。连续若干轮没有有效变化时，提示 Agent 说明证据并切换策略，例如缩小复现、检查调用链或验证另一假设。

首版先做提示与观测，确认误报率后再加入硬限制。相同命令在代码已变化后重跑通常合理；异步任务仍在推进时也不应被误判为死循环。

### 6.3 终端操作的反馈效率

为相互独立的只读探测提供批量执行能力，减少模型往返；有依赖的命令继续按顺序执行。每个命令仍单独记录退出码、输出和耗时，关键失败不会被后续成功掩盖。

优先优化短日志读取、后台任务状态等待和重复环境探测。是否采用更多终端批处理，应作为单独开关验证，保留现有结构化文件工具。

## 7. P2：评测与中断恢复

任务状态建议持久化为：准备完成、解题中、解题结束、评分中、已结束。各阶段有幂等标识，结果落盘原子化。

- 解题结束后保存代码修改、轨迹、预算和测试所需产物。
- 主进程中断后先核查已有产物，不直接重跑模型。
- 评分脚本因包下载或环境准备失败而退出时，记录为评分启动失败，即使脚本写出了 reward 0，也保留其原始值并标注原因。
- 只恢复评分时，校验原代码、原测试与镜像指纹；原始记录、恢复日志和最终解释分别保存。
- 所有模型尝试都进入审计记录，不从多次结果中挑选最好的一次。

扩展位置为 [benchmark 接入](../../benchmarks/README.zh-CN.md)、[对照运行器](../../benchmarks/codenode_benchmarks/comparison.py) 和 [结果处理](../../benchmarks/codenode_benchmarks/results.py)。已有预热与校验应继续保留，同时覆盖本次出现的系统包索引网络问题。

## 8. 指标与验收

| 指标 | 用途 |
| --- | --- |
| 独立测试通过率、配对胜负 | 判断最终任务完成能力 |
| Token 预算停止次数与已用额度 | 判断是否仍在过早结束 |
| 预计剩余轮数、拒绝输入预留、输出预留 | 解释为什么仍有余额却不能发下一轮 |
| 每轮输入分项及累计输入／输出 | 区分固定提示、工具 schema、历史与工具正文的占用 |
| 重复正文体积、重复读取率 | 验证上下文回收是否有效 |
| 压缩次数、成本、压缩前后体积 | 判断压缩是否带来净收益 |
| 首次有效复现、首次正确修改与验证轮数 | 判断求解流程是否更快收敛 |
| 未评分、环境恢复与中断记录 | 避免把基础设施问题当作能力差距 |

首阶段实验目标：已有成功题不退化；预算停止减少；在同一上限下至少补过一道失败题。此目标用于决定是否继续推广，不是收益承诺，也不代替独立留出集验证。

“首次正确修改”以可见测试证据或运行结束后的独立回放核验，不以模型自述为准；事后评分结果不回流到正在解题的 Agent。

离线测试至少覆盖：

- 未触发回收时行为保持不变。
- 输入预算不足且存在可回收内容时，先回收再重算；不可回收时明确结束。
- 摘要失败、无收益或额度不足时不会无限重试。
- 预算、父子额度、未知 usage 和费用上限不能被恢复流程绕过。
- 工具调用与结果配对完整，关键约束、最新修改和失败反例保留。
- 文件修改后引用和缓存正确失效，原始产物能按引用取回。
- 无进展检测不误拦正常等待和修改后的复测。

现有相关命令如下；实施时按实际改动范围选用，并补充上述缺失场景：

```sh
npm run test:request-budget
npm run test:cost-budget
npm run test:compaction
npm run test:compaction-tail
npm run test:context-budget
npm run test:coding-loop
npm run test:agent-reliability
npm run test:benchmark-adapter
npm run test:development-log
```

## 9. 分阶段验证与推广

| 阶段 | 改动范围 | 验证方式 | 推广条件 |
| --- | --- | --- | --- |
| A | 预算感知回收与受限收尾 | 离线轨迹分析、边界测试、固定题回归 | 保住成功题，预算停止下降，无预算越界 |
| B | 旧正文回收、版本化引用与分页策略 | 与 A 单独对照，比较输入体积和通过率 | 重复输入下降，引用可取回，任务表现不退化 |
| C | 验证闭环与无进展策略 | 独立开关逐项实验 | 减少无进展轮数，提高实际通过率 |
| D | 评测恢复和持续回归 | 中断、网络失败、重复启动的故障注入 | 结果不丢失，不重复付费推理，原始证据完整 |

每个行为改动提供独立开关和回滚路径。每轮只改变一组核心变量，冻结模型、预算、题目版本、运行归档与尝试规则；原始成绩、评分恢复和异常排除分别报告。

现有固定题集用于回归与诊断。改动稳定后，再选取未参与调试的新题作为留出集；先登记题数、重复次数和资源预算，再执行。对已知题目的改善不能直接宣称为泛化能力提升。

## 10. 首个实施批次

建议首个批次只交付以下内容：

1. 每轮预算分项与预计剩余轮数的观测信息。
2. 请求前的预算感知回收入口，复用现有去重和压缩组件。
3. 一次有界救援及验证、交付所需额度的规划。
4. 预算不足、压缩失败、工具配对和取消场景的回归测试。
5. 固定配置下的 A/B 记录与可回滚开关。

先用这一批确认相同资源下是否能减少提前停止，再决定后续上下文产物化和求解策略改动的投入。
